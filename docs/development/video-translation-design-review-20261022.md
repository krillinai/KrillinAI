# 视频翻译方案复审：复用已有能力，缩小首版改造

> 状态更新（2026-10-22）：首版实施出现超长字幕和新的错译，流程替换已经撤回。下文是当时的设计判断，不能继续作为当前实现的验收结论；当前决策见[撤回与修复记录](video-translation-legacy-repair-20261022.md)。

日期：2026-10-22。性质：对[逐段确认稿](video-translation-quality-plan-20261022.md)的独立设计审查。用户已确认本次收紧建议，音频和 VTT 首版已实施；实际行为、验证结果和未覆盖边界见[实施记录](video-translation-implementation-20261022.md)。下文保留审查时的论证和建议，第 6 节为实施前验证。

## 1. 审查结论

成功优先、可选步骤失败后降级、保存有效译文、局部恢复和如实交付的方向合理，应保留。原方案存在未经验证的组合设计、固定参数依据不足及质量触发机制含糊的问题，不宜直接整体实施。

首版应修复明确缺陷，复用 OpenCreator 已有内容翻译、来源映射、检查点和回退能力，吸收 VideoLingo 的语义单位和小批次组织。需要改进的是流程连接和边界，不需要另建完整翻译框架。

最重要的修订建议：主请求先可靠取得并保存译文；显示切分按需进行。“翻译与切分合并调用”只作为后续候选，不能因为少一次请求就默认更可靠。

## 2. 哪些结论有证据，哪些还没有

| 证据 | 能支持的判断 | 不能支持的判断 |
| --- | --- | --- |
| 既有 25 分钟视频同源同模型冷启动对照，两边均退出 0 并产出字幕 | 两边都有可完成字幕的实际链路；可定位具体输出问题和成本分布 | 不能据一次运行推断总体成功率，不能说 OpenCreator 本轮完全翻译不了 |
| 原生 VTT source-only 对照及失败回归 | OpenCreator 存在跨时间重复单词被删除的确定性缺陷 | 不能用共同词级输入的完整覆盖证明原生 VTT 解析正确 |
| 模型原始响应中的 `text` / `target_text` 偏差 | 默认读取路径会丢弃已有译文并增加重试 | 不能据此认定所有重试都无意义 |
| 本轮 OpenCreator 14 项定向回归通过 | 内容/排版分离、局部重试、保存、缓存恢复等既有机制有离线测试支撑 | 不证明新组合、新分段策略或 GUI 恢复已经通过验收 |
| 本轮 VideoLingo 17 项定向回归通过 | 机械拆分降级、润色失败回退、双语切分失败保留整条等机制有离线测试支撑 | 不证明机械切分有正确语义，也不证明其全片翻译质量更好 |
| 此次确认稿的新参数和合并请求设计 | 可以形成待测候选 | 没有证据证明“3 个单元、前 2 后 1、翻译与排版合并”是更优默认 |

完整旧对照见[审计报告](../../../benchmarks/os0V5ADLVjM-audit-20261021/REPORT.md)。审查阶段没有重新调用模型，也没有重新运行全片、ASR 或 GUI 测试；后续实施验证另见实施记录，不能与旧对照混为同一次实验。

## 3. 审查发现及建议

### 3.1 高优先级：不应把翻译与切分合并设为首版默认

确认稿希望一次调用取得译文和字幕切分，即使将两者分别验收，仍然共用同一次模型生成与 JSON 响应。切分要求会增加输出长度和约束；整份响应被截断或损坏时，译文也可能无法可靠读取。字段可选不能消除这种共同失败的可能性。

OpenCreator 已有 `translateContentBatch`：内容请求只带来源 ID、原文及语境，保存完整译文，短句可不再请求排版。`recoverPairedSentence` 在片段无效时恢复整句配对，而不是丢掉译文。相关测试已重跑通过。VideoLingo 也先保存翻译结果，再处理超长字幕。

建议首版：

- 主翻译只要求 ID 与完整译文，成功即保存。
- 短字幕直接使用；本地可安全重排的情况先本地处理。
- 只有仍需处理的超长单元，才使用现有配对排版能力；外层收敛为一次局部候选调用，校验不通过即回退完整单元。不要再次进入多层切分、改写、核验循环。
- 同一语义单元内保存完整译文，不要求模型为相同正文同时输出全文和多份重复片段。
- 合并调用如以后需要提速，应在固定来源及模型下单独对照，不直接替换默认。

这可能让少数长字幕多一次请求，但不意味着每个单元都必须增加请求；短句已存在无额外排版调用的快速路径。是否最终更快、更省、成功率更高，均需实测。

参考：[内容翻译](../../runtime/krillinai/internal/service/translation_content.go)、[整句恢复](../../runtime/krillinai/internal/service/translation_recovery.go)、[短句和内容保存测试](../../runtime/krillinai/internal/service/translation_content_test.go)、[VideoLingo 翻译](../../../VideoLingo/core/_4_2_translate.py)、[按需切分](../../../VideoLingo/core/_5_split_sub.py)。

### 3.2 中优先级：固定 3 个单元和前 2 后 1 缺少对照依据

OpenCreator 当前内容批次已经根据输入和预计输出预算装载，并设置条目上限；音频与 VTT 上限分别为 12 和 10，实际会因预算缩批。当前上下文为前 2、后 2 个单位的有限长度片段。VideoLingo 则采用约 600 字符、最多 10 行，批次外前 3、后 2 行。

新方案没有证据证明统一改成 3 个单元、前 2 后 1 更好。过小批次会重复发送提示词、术语和上下文，也可能拆开共享语义；原文单位重建后，固定数量对应的实际长度还会改变。

建议：先复用现有按预算组批与有限上下文实现，保护同句意群的关联。3 个单元与前 2 后 1 降为参数候选，不作为架构规则或新用户配置。分段改造与上下文数量变化分开验证，避免同时改动后无法解释差异。

参考：[OpenCreator 组批](../../runtime/krillinai/internal/service/paired_translation.go)、[现有上下文](../../runtime/krillinai/internal/service/translation_content.go)、[VideoLingo 批次](../../../VideoLingo/core/_4_2_translate.py)。

### 3.3 高优先级：自动质量校准缺少可靠触发来源

“发现表达生硬就校准一次”没有说明由谁、怎样发现。规则不能可靠评价流畅度；若为发现问题而给全部字幕再加模型评分，就重新引入了此前已取消的全量审查。即使改动后的 JSON 合法，也不能证明意思保留得更好。

建议首版不新增自动流畅度检测。质量优化复用已有编辑/修订能力，由用户主动操作，或针对已有证据、已明确指出的局部错误执行。保留初稿与失败回退，不新建“评分 → 润色 → 再评分”链路。语义可疑项与确定错误分开，不能以简单数字/否定字符串差异自动定罪。

VideoLingo 的可选表达阶段及其失败回退值得借鉴，但“有润色能力”不等于“已经可靠自动识别出哪些句子该润色”。默认首版不增加第二轮表达调用，这意味着部分语言表达收益留到下一阶段，不能承诺质量立即超过开启表达优化的 VideoLingo。

参考：[VideoLingo 可选润色与回退](../../../VideoLingo/core/translate_lines.py)、[OpenCreator 既有修订](../../runtime/krillinai/internal/service/translation_revision.go)。

### 3.4 高优先级：语义分段必须改，但不能复制一套分段框架

当前 OpenCreator 的 800 字节保护先于 NLP，NLP 再成为父句内提示。本片已出现姓名、`all | of this` 等错误边界。调整这个顺序有明确证据，是必要改造。

OpenCreator 的 `subtitle_nlp.py` 已吸收 VideoLingo 标点、逗号和连接词方案，并从原文切片保留来源文字；无需再复制一套 NLP 或单独增加一轮全片标点恢复模型。

建议先利用已有 NLP 与规则形成可用语义单位，保留紧密关联，失败允许降级。模型仅处理超长且无法取得可用边界的片段，不能仅因超过一个短的建议词数就给所有片段增加模型预处理。

“每个长段最多一次”仍可能形成大量串行调用；旧对照中，81 次 NLP 切口细化加语境处理，使首次正文请求在第一条模型请求约 450.7 秒后才开始。这个结果不能用“每段调用次数有限”来忽略。需记录实际辅助调用数量和首批译文等待时间，并避免串行扫完全部可选细化后才允许翻译。

NLP 切口始终是启发式，不能保证每段语义独立，也不应增加一个必须由模型判定“分句质量合格”的门槛。

参考：[现有预分句顺序](../../runtime/krillinai/internal/service/subtitle_sentence_semantic.go)、[已有 NLP](../../runtime/krillinai/internal/service/subtitle_nlp.py)、[NLP 提示细化](../../runtime/krillinai/internal/service/subtitle_nlp.go)。

### 3.5 中优先级：术语先于 NLP 不必成为硬性执行顺序

用户确认的是翻译前获得全文重点术语。实际实现中，OpenCreator 已用来源句 ID 给术语附适用范围；VideoLingo 也是分段后再提术语。为了严格保持“先术语、后分段”，再新增一套术语到新句子的映射，属于可避免的复杂度。

建议内部执行先完成本地来源整理和分段，再复用现有术语提取、作用域与缓存。术语仍覆盖全文、在翻译前准备，失败可用空表，不增加用户步骤。

保留已有简短主题及相关语境有价值，不能把简化误解为仅保留孤立词表。简短主题可以与术语在同次请求取得；首版不新增额外主题生成、术语审校或新的多级摘要体系。VideoLingo 当前只取前 `summary_length` 字符，不应复制其后半段覆盖不足的限制。

参考：[已有语境与术语](../../runtime/krillinai/internal/service/translation_semantic_context.go)、[VideoLingo 术语输入](../../../VideoLingo/core/_4_1_summarize.py)。

### 3.6 高优先级：保存机制应复用，恢复入口与快照必须接通

OpenCreator 已有单句原子检查点、正确项保留、坏缓存局部失效，以及排版配置不使内容指纹失效的设计。上述能力不需要另建通用检查点框架、缓存依赖图或持久化任务调度器。

真正的缺口是工作台重试创建新的 stage 目录，没有自然继承旧检查点，以及部分结果没有完整进入稳定结果状态。优先修复这些连接。

还需固定本次采用的分段与术语/语境快照。可选术语第一次失败、恢复时成功，不能自动生成新内容指纹并让此前所有有效译文失去复用机会。现有 segmented 路径已有“降级语境计划续跑不改变”的实现和通过测试，可选择性复用；不需要把整个 segmented 多阶段路径直接设为默认。

参考：[检查点](../../runtime/krillinai/internal/service/translation_checkpoint.go)、[语境计划快照](../../runtime/krillinai/internal/service/translation_semantic_context.go)、[已有恢复测试](../../runtime/krillinai/internal/service/translation_recovery_test.go)、[stage 目录](../../apps/daemon/src/creator/stage-runner.ts)。

### 3.7 高优先级：程序排版兜底不能凭比例制造双语对齐

合法时间戳只能证明格式合法，不能证明两种语言此时表达了对应意思。中文和英文各自按字数切成两半，再分配同样时间，会制造看似整齐的错位。

因此：程序可以在同一 cue 内换行，或合并已经对应的相邻配对；新增有独立时间的双语切口时，必须有对应来源范围。无法可靠细分就回退到整个翻译单元及它已有的时间范围，接受已确认的超长提示交付。

这条约束 OpenCreator 现有 `recoverPairedSentence` 已体现。VideoLingo 的“双侧一起成功才拆分，否则保留整条”同样值得保留。来源 ID、覆盖和时间映射是必要保护，不属于应删除的过度设计；不必要求每个显示碎片都独立完整或逐词对应。

### 3.8 中优先级：明确内容生成和传输重试的不同预算

“最多额外两次”指一次初译及两次内容生成尝试，不等于最多三次 HTTP 请求。当前 `requestTranslation` 自带有上限的临时故障退避；若多次传输故障后返回的正文仍无效，内容尝试与传输尝试可能叠加。

建议复用统一请求封装，记录实际请求次数和内容尝试，防止批次缩小、整句兜底、工作台续跑再次重置自动内容预算。不在每个新阶段复制重试器。鉴权、取消和已经耗尽的临时故障不应再作为普通内容错误逐句循环。

参考：[请求退避和整句恢复](../../runtime/krillinai/internal/service/translation_recovery.go)、[内容尝试循环](../../runtime/krillinai/internal/service/translation_content.go)。

## 4. 收紧后的首版候选

以下明确四段内部职责，不增加用户操作步骤：

1. **来源和分段**：解析/转录后保留来源与时间，复用 NLP 和规则建立句子/意群，疑难长段有降级，不以 800 字节或显示行长定义语义。
2. **翻译前参考**：复用全文术语与已有简短主题，失败可跳过，并固定本次参考快照。
3. **内容翻译**：复用按预算组批与有上限的原文上下文；主请求只取得译文，合格项立即保存，缺失/无效项最多额外两次内容生成。
4. **字幕交付**：短项直接输出，必要时做一次局部配对排版候选；失败使用完整翻译单元时间交付并提示。只在无可靠时间时交付文本并保留字幕待处理状态。

质量校准作为按需能力，放在可用结果之后；默认主线不增加全量评分、必经润色、改后再审。恢复与局部状态复用既有机制并贯通工作台，不另造任务系统。

与确认稿相比，主要变化是：内部先本地分段再复用术语；主调用只翻译；固定批次/上下文数字降为待测参数；自动质量触发收紧为明确的按需入口。成功优先、两次内容重试、一次按需校准和交付底线不变。

## 5. 实施与验收建议

1. 先只修确定性缺陷：VTT 丢词、无歧义响应字段兼容、工作台恢复和实际未译状态。先验证已有主线，不同时改变所有生成策略。
2. 再单独调整语义单位，复用当前内容翻译、上下文及保存路径，保留旧成品作比较。
3. 最后收敛局部排版，移除默认链路里的重复修复依赖。验证错误切分不会影响有效译文，不能靠放宽行长掩盖未译或错误时间。
4. 候选通过后再评估合并调用、上下文数量和自动质量能力。尚未验证的参数不成为默认路径的先决条件。

真实验收至少覆盖音频与原生 VTT、NLP/术语不可用、部分响应、排版失败、鉴权、取消、重启与工作台继续。检查最终字幕和原生来源；不能只检查文件存在、单元测试或模型自评分。

既有对照中，OpenCreator 的显示相关阶段占 520,713 / 669,998 token，约 77.7%。应先减少错误单位和多层排版修复，不应优先为省少量语境调用而重写整套参考机制。该分布是一次实测证据，不是新方案成本承诺。

## 6. 实施前的审查验证

- OpenCreator：当前工作区 `go test ./internal/service`，精确选择内容负载、局部重试、短句恢复、取消保存、排版断连、缓存恢复与语境降级快照等 **14 个顶层测试**，全部通过（包括参数子测试）。日志 `/tmp/opencreator-design-review-tests-20261022.jsonl`。没有跑完整服务测试套件。
- VideoLingo：现有 `tests/test_backlog_fixes.py` 中相关 **17 个用例通过，208 个未选择**。覆盖机械拆分回退、取消传播、翻译额外字段、润色回退、初译失败、按需配对切分及配对失败保留整条。
- Python 测试工具临时安装在 `/tmp/videolingo-design-review-pytest-20261022`，未修改项目依赖。测试使用既有基准虚拟环境，没有下载 NLP 模型，也没有请求翻译服务。
- 审查阶段没有修改业务代码、提交、推送或部署；主工作区既有 NLP/打包改动保留。

这些检查支持复用已有机制，不构成新候选已成功跑通或质量已经提升的证据。审查结论是缩小方案后再实施验证，不能向用户保证尚未测得的成功率。

## 7. 确认后的实施状态

已按收紧后的四段职责接入音频和 VTT，复用现有内容翻译、语境和检查点；原始 SRT 保留原策略。默认不增加自动质量评分、必经润色或多层排版修复。全文模型辅助分句也未加入首版，无法取得自然边界时使用可追踪的本地预算降级。

真实原生 URL/VTT 入口已运行，并针对运行发现的排版读取问题完成原响应重放；音频完成 FFmpeg 与受控 ASR 协议集成验证。最终结果、测试范围、7 个排版待调整单元及尚未验证的真实 ASR/GUI 见[实施记录](video-translation-implementation-20261022.md)。没有提交、推送或部署。
