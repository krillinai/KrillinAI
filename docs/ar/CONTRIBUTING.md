شكرًا لتفكيرك في المساهمة. OpenCreator هو مساحة عمل للمبدعين تعمل محليًا أولًا ومبنية على حلقة وكيل Codex، ومعظم قيمته تأتي من إضافات صغيرة ومركّزة: مجلد Skill واحد، قالب إنشاء واحد، أو إصلاح واحد محدد النطاق. يوضح هذا الدليل أين يجب أن يكون كل نوع من المساهمات وما المعايير التي يجب أن يستوفيها طلب الدمج قبل قبوله.

## خريطة المساهمات

| إذا كنت تريد… | فأنت في الواقع تضيف | أين يوجد | حجم التسليم |
|---|---|---|---|
| إصلاح خطأ أو تحسين سير عمل | كود | `apps/web/`، `apps/daemon/` | طلب دمج واحد مركّز مع اختبارات |
| إضافة سير عمل قابل لإعادة الاستخدام للوكيل | **Skill** | [`skills/<skill-الخاص-بك>/`](../../skills/) | مجلد واحد يحتوي `SKILL.md` ومراجع اختيارية ← [الدليل](./contributing/skills-contributing.md) |
| إضافة إعداد مسبق قابل لإعادة الاستخدام للصور أو الفيديو أو الأغلفة | **قالب إنشاء** | [`template/<module>/<id>/<version>/`](../../template/) | مجلد واحد يحتوي `template.json` وأصوله ← [الدليل](./contributing/templates-contributing.md) |
| المساهمة برسوم توضيحية أو أيقونات أو تصاميم واجهة | أصول تصميم | موقع أصول متفق عليه | طلب دمج واحد مع معاينات وملفات مصدر وترخيص |
| ربط خدمة ذكاء اصطناعي أو وسائط | **تكامل خدمة** | وحدة Web أو Daemon ذات الصلة | طلب دمج واحد مع معالجة الأخطاء وأمان بيانات الاعتماد واختبارات |
| تحسين التوثيق أو الترجمات | مستندات | `README.md`، `docs/`، `docs/<locale>/README.md` | طلب دمج واحد |

إذا لم تكن متأكدًا من الفئة التي تنتمي إليها فكرتك، [افتح مشكلة أولًا](https://github.com/krillinai/OpenCreator/issues/new) وسنوجهك إلى المكان الصحيح.

## الإعداد المحلي

الإعداد الكامل موجود في [البدء السريع في README](../../README.md#quick-start). الملخص للمساهمين:

```bash
git clone https://github.com/krillinai/OpenCreator.git
cd OpenCreator
corepack enable          # يختار إصدار pnpm المثبت في packageManager
pnpm install
pnpm web:dev             # ‏web + الخادم المحلي عند الطلب
pnpm typecheck           # فحوصات TypeScript عبر المستودع
pnpm test                # اختبارات الوحدة والتكامل في مساحة العمل
```

مطلوب Node.js 22+ وملف Codex CLI تنفيذي. افتح `http://127.0.0.1:19861/` بعد `pnpm web:dev`؛ يجهّز Runtime مشروعًا افتراضيًا عند التشغيل الأول ويصبح محرر الإدخال جاهزًا فور اكتمال الاتصال.

## كيفية المساهمة

1. صِف المشكلة وحالة الاستخدام والسلوك المتوقع في [مشكلة](https://github.com/krillinai/OpenCreator/issues).
2. أنشئ فرعًا مركّزًا للميزة أو الإصلاح من أحدث فرع تطوير.
3. اتبع البنية الحالية: تُنفَّذ القدرات العامة للمنتج **مرة واحدة** في Web وDaemon، وتُعزل الاختلافات الأصلية في Desktop خلف قدرات صريحة (مثل `canSelectDirectory`).
4. أضف تغطية اختبارات وحدة أو تكامل أو E2E مناسبة لتغييرات السلوك، واذكر في طلب الدمج التحققات المنفَّذة والمتخطّاة معًا.
5. لا تُدرج أبدًا `.runtime/` أو بيانات الاعتماد المحلية أو جلسات Codex أو ذاكرات التخزين المؤقت للبناء أو غيرها من بيانات المستخدم.

## ما يتحقق منه المراجعون

- **تنفيذ واحد للسلوك المشترك.** يجب ألا تُنفَّذ الميزة نفسها بشكل منفصل لـ Browser Bridge وDesktop Bridge.
- **التحكم بالقدرات وليس الكيانات الوهمية الصامتة.** يجب إخفاء المدخل الخاص بالمنصة عندما تكون القدرة غير متاحة — لا تعرض أبدًا زرًا لا يفعل شيئًا بصمت.
- **الاختبارات تتناسب مع مخاطر التغيير.** تعديلات النصوص أو الأنماط الصغيرة تحتاج فحوصات موجهة فقط؛ تغييرات الحالة المشتركة أو الاستمرارية أو عقود Runtime تتطلب على الأقل اختبارات الوحدة المعنية وtypecheck.
- **التوثيق يُحدَّث مع السلوك.** إذا غيّر تعديلك سير عمل مرئيًا للمستخدم، حدّث README أو المستند ذا الصلة في `docs/` ضمن طلب الدمج نفسه.

## الأسباب الشائعة لإرجاع طلبات الدمج

- أُضيف المنطق نفسه بشكل منفصل في مساري Web وDesktop بدلًا من طبقة الخدمة المشتركة.
- زر غير مدعوم من المنصة ظاهر لكن معالجه يعود بصمت.
- تغيّر السلوك دون اختبارات أو ملاحظة تحقق.
- طلب الدمج يخلط إعادة هيكلة أو إصلاحًا غير مرتبط بالتغيير الرئيسي.
- أُدرجت ملفات مولّدة أو بيانات `.runtime/` أو بيانات اعتماد.
